Ubuntu Chisel — carve away cruft to create minimal Ubuntu for containers

Same signed Ubuntu binaries, ten times smaller, no shell and no package manager — and Microsoft already ships their .NET production containers using it.

3 May 2026 18 min read

Why yes, yes I do want tiny Ubuntu container images without SSH shell at all.

Microsoft recommends chiselled Ubuntu for new .NET containers (https://github.com/dotnet/dotnet-docker/blob/main/documentation/ubuntu-chiseled.md), and Canonical maintains a growing catalogue of pre-built chiselled rocks for the things people actually run in production: PostgreSQL (https://github.com/canonical/postgresql-rock), Python (https://github.com/canonical/python-rock), Java/JRE (https://github.com/canonical/jre-rock), Node.js (https://github.com/canonical/node-rock), nginx (https://github.com/canonical/nginx-rock), and RabbitMQ (https://github.com/canonical/rabbitmq-rock). Canonical's oci-factory repository (https://github.com/canonical/oci-factory) provides the reusable GitHub Actions workflow that builds, tests, and publishes rocks at scale, including Trivy (https://github.com/aquasecurity/trivy) scanning and Pebble service-manager smoke tests.

Sounds important — so what is it?

Chisel (https://github.com/canonical/chisel) is a Canonical project that lets you carve Ubuntu's Debian packages into named subsets — slices — and ship only the slices an application actually needs into a container image. The output is the same signed binaries the Ubuntu archive ships to production servers, just without the manpages, shell utilities, locale data, and the hundred other files most applications never use. Production images come out five to ten times smaller than the equivalent built from a normal Ubuntu base. CVE counts drop because the vulnerable files are no longer present. Canonical publishes chiselled rocks for PostgreSQL, RabbitMQ, JRE and Python. The tool is a single Go binary licensed under AGPL-3.0.

Pull a fresh ubuntu:22.04 from Docker Hub and check the size: about 28 megabytes compressed, around 80 megabytes uncompressed. That's the base, before anything else is installed. For an application built as a single static Go binary, almost none of those 80 megabytes will ever be touched at runtime. The shell, apt, dpkg, the locale archive, the manpages, the hundred-odd files in /usr/share/doc, the readline library — all shipped, all stored in the registry, all pulled by every node in the cluster, all scanned by every CVE scanner, none of it executed.

This is the container-size problem, and people have been working at it for years now.

The most common existing answer is Alpine Linux (https://www.alpinelinux.org). Swap glibc for musl, swap GNU coreutils for busybox, and a base image that was 78MB compressed shrinks to about 3MB. The trade-off is musl/glibc compatibility. DNS resolver behaviour differs in subtle ways. Quite a few Python wheels won't install because they were built against manylinux and don't have musl variants. Go's cgo paths need rebuilding against a different libc, too.

A second answer is Google Distroless (https://github.com/GoogleContainerTools/distroless). Take a runtime — Java, Python, Node, .NET — strip out the OS plumbing, ship only what's needed for that runtime, with no shell or package manager. The images are small and hardened, but they are Google's curated set, on Google's release cadence, supporting the runtimes Google has chosen to support. If your stack doesn't fit the curated set you fork it and maintain it yourself.

A third answer is FROM scratch: build the entire image content yourself. For adventurers with a bright lamp and sword of sharp steel.

Canonical's answer is Chisel. The approach in one sentence: instead of shipping whole Debian packages into a container image, ship pre-defined named subsets of those packages — slices — that contain only the files needed.

The canonical Chisel command, straight from the README:

chisel cut --release ubuntu-22.04 --root ./myrootfs \
    libgcc-s1_libs libssl3_libs

The --release ubuntu-22.04 argument tells Chisel which branch of the chisel-releases repository (https://github.com/canonical/chisel-releases) to read slice definitions from. Slice definitions are versioned per Ubuntu release: there's an ubuntu-22.04 branch, an ubuntu-24.04 branch, an ubuntu-22.10 branch, and so on, all in a single repository. The arguments on the end — libgcc-s1_libs and libssl3_libs — are slice names, following the convention <package>_<slice>, where package is an actual Debian package in the Ubuntu archive and slice is one of the named subsets the slice-definitions YAML for that package declares.

When that command runs, Chisel reaches out to the Ubuntu archives, downloads the actual signed .deb files for the requested packages and any transitive dependencies, validates the GPG signatures against the Ubuntu archive key, opens the debs, picks out only the files declared by the requested slices and their dependent slices, and writes those files into myrootfs/. The files are bit-identical to what apt install would produce — same archive, same signatures, same bytes — there are simply fewer of them.

A fragment of slice-definition YAML, from the project README:

package: mypkg
slices:
    bins:
        essential:
            - mypkg_config
        contents:
            /bin/mybin:
            /bin/moved:  {copy: /bin/original}
            /bin/linked: {symlink: /bin/mybin}
    config:
        contents:
            /etc/mypkg.conf: {text: "The configuration."}
            /etc/mypkg.d/:   {make: true}

Each slice has a contents: block listing paths. A bare path means "take this file from the .deb verbatim". There's a handful of other attributes too: make: true creates a directory, copy: extracts a file from one location in the deb and writes it to a different location in the rootfs, symlink: creates a symlink, text: writes literal content into a new file, mode: sets octal permissions, arch: restricts a path to specific architectures (so arch: amd64 ships the file only when chiselling an amd64 image), and until: mutate means the file should exist during installation but be removed afterwards once the mutation script has run.

A slice can also include a mutate: block written in Starlark (https://github.com/google/starlark-go) — Google's Python-flavoured config language — that runs after files are extracted and can read content from one extracted file and write derived content into another. This is how Chisel handles cases where a Debian package would normally execute a maintainer script at install time. Rather than executing update-alternatives or a postinst script, the intent is expressed declaratively in Starlark and Chisel runs it.

The slice catalogue in chisel-releases covers the major language ecosystems: Python 3.x, Java/JRE, .NET runtime dependencies, Node, and Go libraries. Common server software is sliced — openssl, libcurl, libxml2, libsqlite, the ICU data, ca-certificates split into _data and the libraries that read it, the major database client libraries, and the major TLS stacks. The standard system libraries are sliced too: glibc as libc6_libs, libgcc, and the C++ runtime. The README documents current limitations: package names must match the Debian archive (no aliases), only Ubuntu repositories are supported, and multiple repositories cannot be combined in one Chisel release.

Chisel supports Ubuntu Pro (https://ubuntu.com/pro) archives. In chisel.yaml an archive can be declared with a pro: field that takes one of fips, fips-updates, esm-apps, or esm-infra, and Chisel pulls from the corresponding endpoint at esm.ubuntu.com using credentials from /etc/apt/auth.conf.d/. This allows building a chiselled image whose binaries come from FIPS-validated builds with ten-year security maintenance. The credentials file's default permissions are root-only, so the file must be made readable by the user running Chisel via chmod or setfacl.

Building actual images

Chisel cuts files into a directory. Turning that directory into a runnable container image requires wrapping it. The manual approach is a FROM scratch Dockerfile that does COPY --from=builder /myrootfs / and sets an ENTRYPOINT. Microsoft's official guidance for installing custom slices into chiselled .NET images, in the dotnet/dotnet-docker repository (https://github.com/dotnet/dotnet-docker), follows exactly this pattern: build a chisel stage, run chisel cut against a target directory, then COPY --from=chisel /rootfs / into a final scratch image. The Microsoft pattern also uses chisel-wrapper from the rocks-toolbox project (https://github.com/canonical/rocks-toolbox), a small helper that generates a dpkg/status file inside the rootfs so vulnerability scanners can still identify the installed packages.

The higher-level option is Rockcraft (https://github.com/canonical/rockcraft), Canonical's tool for building OCI images on top of the same Craft Parts lifecycle that drives Snapcraft (https://snapcraft.io) and Charmcraft (https://github.com/canonical/charmcraft). The rockcraft.yaml syntax mirrors snapcraft.yaml: parts, stage-packages, plugins, the same five-stage pull/overlay/build/stage/prime lifecycle. The output is what Canonical calls a "rock" — an OCI-compliant image, runnable by Docker, Podman, Kubernetes, anything that speaks OCI — built with two opinionated conventions.

The first convention is the entrypoint. A rock's entrypoint is Pebble (https://github.com/canonical/pebble), a Go-based service manager Canonical wrote to handle process orchestration, log aggregation, and graceful shutdown inside a container. Services are declared as a Pebble plan in the rockcraft.yaml and Pebble runs them, replacing the usual Dockerfile CMD and shell wrapper.

The second convention is that stage-packages accepts chisel slice names interchangeably with normal package names. This:

parts:
  app:
    plugin: nil
    stage-packages:
      - openssl

ships the full openssl Debian package and its dependencies, while this:

parts:
  app:
    plugin: nil
    stage-packages:
      - openssl_bins
      - ca-certificates_data

ships only the openssl binary, the libraries it links against, and the CA certificate bundle. Setting base: bare at the top of the file produces an image with no Ubuntu base layer underneath at all — no /bin/sh, no /etc, no apt — and what is shipped is exactly what the slices declared. One current limitation is that a single stage-packages list must be all slices or all full packages, not a mix; the workaround is splitting them across parts.

Some concrete sizes. Canonical's walkthrough at https://ubuntu.com/blog/craft-custom-chiselled-ubuntu-distroless builds a minimal base of base-files_base, base-files_release-info, ca-certificates_data, and libc6_libs, and lands at around 5MB. The Microsoft/Canonical .NET work, which went GA in November 2023 and ships as mcr.microsoft.com/dotnet/runtime-deps:8.0-jammy-chiseled, gets .NET 8 self-contained AOT applications down below 10MB; Microsoft's announcement post at https://devblogs.microsoft.com/dotnet/announcing-dotnet-chiseled-containers/ documents the figures and recommends chiselled images for new .NET container deployments. Canonical reports a 51% reduction in compressed image size for the chiselled JRE versus the Eclipse Temurin Java 17 runtime. The ASP.NET eShop comparison at https://ubuntu.com/blog/benefits-chiselled-ubuntu-images-aspnet-eshop-demo reports a roughly 20% improvement in container startup time, a 7% reduction in steady-state memory, and a 21% reduction in memory under load.

A real-world example of a rockcraft.yaml is the PostgreSQL rock (https://github.com/canonical/postgresql-rock) — the packaging metadata Canonical uses to ship ubuntu/postgres as a rock. Pulling and running it:

docker run -it -d \
  -e POSTGRES_PASSWORD=myS3cr3tp@ss \
  -p 3432:5432 \
  --volume pg-data:/var/lib/postgresql/ \
  ubuntu/postgres:16-24.04_edge \
  --args postgres \
  -c max_connections=242 \
  -c fsync=off \
  -c shared_buffers=256MB

The --args postgres -c max_connections=242 syntax is Pebble's, not Docker's. The container's actual entrypoint is Pebble, which runs its declared postgres service plan with the supplied command-line arguments. Inside the rock, the postgres binaries are the same binaries from the Ubuntu postgresql-16 Debian package — the same package apt install postgresql-16 would put on a regular Ubuntu host. Same archive, same signature, same security update pipeline. When a libpq CVE drops, the same fix flows into the deb, the snap, the chiselled rock, and the full rock, on the Ubuntu Security cadence. Building a rock locally is three commands once rockcraft is installed:

git clone https://github.com/canonical/postgresql-rock.git
cd postgresql-rock
rockcraft pack

The repository wires up rockcraft test, which runs spread tests against the built image — there are smoke and upgrade suites, a single suite can be targeted with rockcraft test -- spread/tests/smoke, and rockcraft test --debug opens a shell into a failed test environment. Canonical maintains similar repositories for other infrastructure components: rabbitmq-rock (https://github.com/canonical/rabbitmq-rock), jre-rock (https://github.com/canonical/jre-rock), python-rock (https://github.com/canonical/python-rock), and charmed-postgresql-rock (https://github.com/canonical/charmed-postgresql-rock).

What chiselling provides, and what it costs

The size reduction is the most visible effect but it isn't the only one.

A properly chiselled image contains no shell, which removes the most common foothold used by lateral-movement tooling that assumes a popped container provides shell access. A chiselled image contains no package manager, which means an attacker who lands code execution cannot use apt install netcat-openbsd to bring in additional tooling — the tooling has to be brought in through some other channel. Neither of these is an absolute defence: a static binary can still be downloaded if curl is present, and the running process itself can still be abused.

CVE counts decrease because file counts decrease. Vulnerability scanners flag vulnerable files; if a file is not present in the image, it cannot be flagged. The vulnerability still exists upstream, but the image stops carrying the affected component, and the scanner stops reporting on a bash bug in an image that contains no bash.

There are real trade-offs. Only sliced packages can be installed; the catalogue covers a large set of common software but is not comprehensive across the entire Ubuntu archive, so missing slices may need to be defined and PR'd upstream. The bare base contains no /bin/sh, so applications that rely on system() or shell-outs require modification. The docker exec -it ... bash debugging workflow is unavailable; Canonical's recommended pattern is shipping a separate debug variant of the rock that contains the additional tooling.

The chisel binary is also usable as a general-purpose package extraction tool on any Linux host. It does not require root if it is writing into a directory the user owns. A command like chisel cut --release ubuntu-22.04 --root /tmp/foo libsqlite3-0_libs will retrieve a single library out of an Ubuntu package without altering the system's apt state. The same mechanism works for build sandboxes, embedded targets, cross-architecture staging directories, and inspecting the runtime contents of a package.

So what do I actually do?

The five-second version. Pull a pre-built chiselled rock and run it:

docker run --rm -d \
  -e POSTGRES_PASSWORD=secret \
  -p 5432:5432 \
  ubuntu/postgres:16-24.04_edge

Done. That postgres container has no shell, no package manager, and a CVE scan against it will come up nearly empty. Same shape for ubuntu/nginx, ubuntu/jre, and the other prebuilt rocks listed at the top of the article.

The build-your-own version. Install chisel, cut a rootfs, wrap it in a scratch image:

go install github.com/canonical/chisel/cmd/chisel@latest

mkdir myrootfs
chisel cut --release ubuntu-24.04 --root myrootfs/ \
    base-files_base \
    ca-certificates_data \
    libc6_libs \
    libssl3_libs

cat > Dockerfile <<'EOF'
FROM scratch
COPY myrootfs/ /
COPY my-app /usr/bin/my-app
ENTRYPOINT ["/usr/bin/my-app"]
EOF

docker build -t my-chiselled-app .
docker run --rm my-chiselled-app

That's roughly 12MB of base plus the application binary on top. Add or remove slices on the chisel cut line until the application's library dependencies are satisfied — ldd your-binary against an Ubuntu host will tell you what to look for.

The Python Flask version. A "hello world" Flask app on a chiselled image needs a multi-stage build: one stage to install Flask via pip into a virtualenv, one stage to chisel a rootfs, and a final scratch stage that combines them.

# app.py
from flask import Flask
app = Flask(__name__)

@app.get("/")
def index():
    return "Hello from a chiselled Flask container\n"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8080)
# Dockerfile
FROM ubuntu:24.04 AS venv
RUN apt-get update && apt-get install -y --no-install-recommends \
        python3 python3-venv && rm -rf /var/lib/apt/lists/*
RUN python3 -m venv /opt/venv && \
    /opt/venv/bin/pip install --no-cache-dir flask

FROM ubuntu:24.04 AS chiseler
ARG CHISEL=v1.4.0
RUN apt-get update && apt-get install -y --no-install-recommends ca-certificates curl \
    && curl -fL https://github.com/canonical/chisel/releases/download/${CHISEL}/chisel_${CHISEL}_linux_amd64.tar.gz \
       | tar xz -C /usr/bin chisel
RUN mkdir /rootfs && chisel cut --release ubuntu-24.04 --root /rootfs \
        base-files_base \
        ca-certificates_data \
        libc6_libs \
        libssl3_libs \
        python3.12_standard

FROM scratch
COPY --from=chiseler /rootfs /
COPY --from=venv /opt/venv /opt/venv
COPY app.py /app/app.py
ENV PATH=/opt/venv/bin:$PATH
WORKDIR /app
EXPOSE 8080
ENTRYPOINT ["python3", "app.py"]

Build, run, hit it:

docker build -t flask-chiselled .
docker run --rm -p 8080:8080 flask-chiselled
# in another terminal:
curl http://localhost:8080/
# Hello from a chiselled Flask container

The final image lands around 30MB. It contains a chiselled Ubuntu base (~12MB), the Python _standard slice (~13MB), and the Flask virtualenv (~5MB). The apt, curl, and pip that built it stayed in the discarded builder stages and are not in the final image — there is no shell, no package manager, and nothing to docker exec ... bash into.

For Pebble service management, a declarative project file and a multi-service deployment, see the worked scenario below.

A worked scenario: Python workers, PostgreSQL, and RabbitMQ

A common deployment pattern is a pool of workers consuming tasks from a message queue and persisting state to a relational database. Here, that's Python workers reading from RabbitMQ and writing to PostgreSQL. All three components can be deployed as chiselled rocks.

PostgreSQL is published as a chiselled rock by Canonical at canonical/postgresql-rock, image tag ubuntu/postgres:16-24.04_edge. RabbitMQ is published at canonical/rabbitmq-rock as a chiselled distroless-style RabbitMQ server image. Both use Pebble as their entrypoint and accept the same environment variables their conventional images do.

The Python worker is built locally using Rockcraft. A minimal rockcraft.yaml:

name: pyworker
base: bare
build-base: ubuntu@24.04
version: "0.1"
summary: Python worker for the job queue
license: Apache-2.0

platforms:
  amd64:

services:
  worker:
    override: replace
    command: /usr/bin/python3.12 /app/worker.py
    startup: enabled
    on-failure: restart

parts:
  runtime:
    plugin: nil
    stage-packages:
      - python3.12
      - python3-pika
      - python3-psycopg2

  ca-certs:
    plugin: nil
    stage-packages:
      - ca-certificates_data

  app:
    plugin: dump
    source: ./src
    organize:
      worker.py: app/worker.py

The runtime and ca-certs parts are split because a single stage-packages list cannot mix full Debian packages with chisel slices. Where the equivalent slice exists in the chisel-releases catalogue for the target Ubuntu branch, full package names can be replaced with slice names (e.g. python3.12_core) for further size reduction; full package names are used here as the conservative default.

The worker source goes in ./src/worker.py:

import os, pika, psycopg2

amqp_url = os.environ["AMQP_URL"]
db_url   = os.environ["DATABASE_URL"]

conn = psycopg2.connect(db_url)
mq   = pika.BlockingConnection(pika.URLParameters(amqp_url))
ch   = mq.channel()
ch.queue_declare(queue="jobs", durable=True)

def handle(ch, method, properties, body):
    with conn.cursor() as cur:
        cur.execute("INSERT INTO results (payload) VALUES (%s)", (body,))
    conn.commit()
    ch.basic_ack(delivery_tag=method.delivery_tag)

ch.basic_consume(queue="jobs", on_message_callback=handle)
ch.start_consuming()

Build the rock with rockcraft pack, which produces pyworker_0.1_amd64.rock. To load it into a local Docker daemon for testing:

sudo rockcraft.skopeo --insecure-policy copy \
    oci-archive:pyworker_0.1_amd64.rock \
    docker-daemon:pyworker:0.1

A docker-compose.yml to run the three components together:

services:
  postgres:
    image: ubuntu/postgres:16-24.04_edge
    environment:
      POSTGRES_PASSWORD: changeme
      POSTGRES_DB: jobs
    volumes:
      - pgdata:/var/lib/postgresql/

  rabbitmq:
    image: ubuntu/rabbitmq:3.12-24.04_edge
    environment:
      RABBITMQ_DEFAULT_USER: worker
      RABBITMQ_DEFAULT_PASS: changeme

  worker:
    image: pyworker:0.1
    environment:
      DATABASE_URL: postgresql://postgres:changeme@postgres:5432/jobs
      AMQP_URL: amqp://worker:changeme@rabbitmq:5672/
    depends_on:
      - postgres
      - rabbitmq
    deploy:
      replicas: 4

volumes:
  pgdata:

docker compose up brings up all four containers. Logs are accessible through docker logs <container> or via Pebble directly with docker exec <container> pebble logs. None of the three images contain a shell, so docker exec ... bash is not available; if interactive debugging is required, Canonical's recommended pattern is to publish a debug variant of the rock with the additional tooling included.

Each container's image contains only the binaries and libraries that component needs at runtime: postgres pulls postgres binaries plus libssl and libc; rabbitmq pulls Erlang, the rabbitmq server, and required libs; the worker pulls python3.12, the AMQP and PostgreSQL client libraries, and the CA certificate bundle. Security updates for any of those components flow through the Ubuntu Security pipeline and into the next build of each rock — the same pipeline that updates the equivalent apt install on a conventional Ubuntu host.
